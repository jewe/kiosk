# tunnel — remote SSH access to kiosks

Each kiosk keeps an outgoing SSH connection to a server and forwards a port there back to its own sshd
(`ssh -R <port>:127.0.0.1:22`). From anywhere you reach the kiosk by jumping through the server. Kiosks need no
open port, no public IP and no VPN; only outgoing SSH to the server.

```
Mac ──ssh -J──▶ server (tunnel.jewe.net) 127.0.0.1:<port> ◀──reverse tunnel── kiosk (behind NAT)
```

- Kiosk side: `services/tunnel/` (`apply.sh` + `kiosk-tunnel.service`), config `services.tunnel`, key pair
  generated on the device into `/opt/kiosk/secrets/tunnel/` (data volume, survives the read-only root).
- Server side: `server.sh` in this directory (user + sshd drop-in + one key line per kiosk). Nothing to install.

## Server

| | |
|---|---|
| Host | `tunnel.jewe.net` → 116.203.22.93 (Hetzner CAX11, also hosts websites; server docs in `~/htdocs/116.203.22.93_cax11/README.md`) |
| SSH | port 22, keys only, fail2ban sshd jail (5 failures in 10 min → 1 h ban per IP) |
| User | `tunnel`, no shell (`/usr/sbin/nologin`), home `/home/tunnel` |
| Keys | `/home/tunnel/.ssh/authorized_keys`, one line per kiosk: `restrict,port-forwarding,permitlisten="<port>" ssh-ed25519 … kiosk:<name>` |
| sshd | `/etc/ssh/sshd_config.d/50-kiosk-tunnel.conf`: `Match User tunnel` → `AllowTcpForwarding remote`, `GatewayPorts no`, no TTY/X11/agent, `ClientAliveInterval 30` × 3 |
| Firewall | nothing to open besides 22; the tunnel ports listen on 127.0.0.1 only |

`restrict` takes away shell, PTY, agent and X11 forwarding; `permitlisten` lets each key listen only on its own
port, so one kiosk cannot take over another's port. A stolen kiosk key gives an attacker nothing but the right to
listen on one loopback port of the server.

Set up a new server (idempotent, safe to re-run; checks `sshd -t` before reload):

```bash
ssh root@tunnel.jewe.net bash -s -- setup < tunnel/server.sh
```

## Add a kiosk

1. Device config (`/opt/kiosk/config/kiosk.yaml`):
   ```yaml
   services:
     tunnel:
       enabled: true
       host: tunnel.jewe.net
       remote_port: 20100        # from the table above
   ```
   `port: 22` and `user: tunnel` are the defaults.
2. **Authorize the key on the server before enabling** (see Pitfalls). Get the key, then add it:
   ```bash
   key="$(ssh kioskadmin@<ip> sudo kioskctl secrets tunnel-key)"   # generated by the first apply with enabled: true
   ssh root@tunnel.jewe.net bash -s -- add <name> <port> "'$key'" < tunnel/server.sh
   ```
   No key yet? `sudo kioskctl apply` with the tunnel enabled generates it (and starts trying to connect), or
   create it beforehand with `sudo ssh-keygen -t ed25519 -N "" -C kiosk-<name> -f /opt/kiosk/secrets/tunnel/id_ed25519`.
3. `sudo kioskctl apply` on the kiosk (or `sudo systemctl restart kiosk-tunnel` if it is already enabled).
4. Check: `ssh root@tunnel.jewe.net bash -s -- list < tunnel/server.sh` shows the device as `up`.
5. Keep a copy of the key pair on the Mac: `tools/secrets.sh pull <name> kioskadmin@<ip>` → `secrets/<name>/tunnel/`.

Remove a kiosk: `ssh root@tunnel.jewe.net bash -s -- remove <name> < tunnel/server.sh`, then
`services.tunnel.enabled: false` + apply on the device (otherwise it keeps failing, see Pitfalls).

## Connect

```bash
ssh -J root@tunnel.jewe.net -p 20100 kioskadmin@localhost
```

Or once per device in `~/.ssh/config`, then `ssh wetho-remote` (also works for `scp`, `rsync`, `tools/secrets.sh`):

```
Host tunnel.jewe.net
    User root

Host wetho-remote
    HostName localhost
    Port 20100
    User kioskadmin
    ProxyJump tunnel.jewe.net
    HostKeyAlias wetho
```

`HostKeyAlias` keeps one known_hosts entry per device; without it all devices share `[localhost]:<port>` entries
and a reinstalled device shows a host key warning (that one is real: check, then `ssh-keygen -R`).
Any user with SSH access to the server can be the jump user; it needs `AllowTcpForwarding` (root on this server has it).

## Kiosk side behaviour

- `kiosk-tunnel.service` runs plain `ssh -N -R …` (no autossh). systemd restarts it with backoff:
  60 s, then growing to 10 min between attempts (`RestartSec=60`, `RestartSteps=4`, `RestartMaxDelaySec=600`).
  The counter only resets on a manual start/restart (`kioskctl apply` does that), so a device with flaky network
  can take up to 10 min to come back after an outage.
- At boot `ExecStartPre` waits up to 60 s until the server name resolves (network-online is reached before DNS
  works; without the wait the first attempt fails and the tunnel comes up only after the 60 s backoff).
- `ServerAliveInterval 30` × 3: a dead connection is noticed within ~90 s. The server does the same
  (`ClientAliveInterval`), so a stale forward frees the port and the reconnect does not hit `ExitOnForwardFailure`.
- Server host key: accepted on first connect (`accept-new`) into `/opt/kiosk/secrets/tunnel/known_hosts`.
  To pin it beforehand: `ssh-keyscan tunnel.jewe.net > secrets/<name>/tunnel/known_hosts` and push.
- Status: `systemctl status kiosk-tunnel`, `journalctl -u kiosk-tunnel`, `kioskctl status` (unit `kiosk-tunnel`).

## Pitfalls

- **fail2ban bans the whole site.** A kiosk whose key is not (yet) authorized fails its login on every attempt.
  5 failures in 10 min ban the site's public IP for 1 h, and with it every other device and admin there
  (seen 2026-11-16: the old autossh unit made 5 attempts in 2 s and locked the office out). Hence: authorize first,
  enable second; and the slow backoff above (4 attempts in the first 10 min). If it happened: stop the unit
  (`sudo systemctl stop kiosk-tunnel`), wait out the hour or unban from elsewhere: `fail2ban-client set sshd unbanip <ip>`.
- **Same port on two devices:** the second one fails with `remote port forwarding failed` and retries forever.
  `server.sh add` refuses a port already used by another key.
- **Working through the tunnel:** `kioskctl apply` restarts `kiosk-tunnel` and with it cuts your own session.
  Run it detached: `sudo systemd-run --unit kiosk-apply-remote kioskctl apply`, reconnect after ~1 min, read the
  result with `journalctl -u kiosk-apply-remote`. Same for anything that touches the network.
- **Reinstalled device:** new key pair → `add` again with the same name (replaces the old line).
